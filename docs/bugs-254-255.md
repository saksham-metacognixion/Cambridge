# Bugs 254-255: the editor's paragraph button and the Publish site button (dashboard)

Date: 30 Oct 2026. Nothing committed or deployed. Dashboard = `tools/admin/` (SEO & GEO dashboard).

## Bug 254: H2 / H3 / Quote never went back to a paragraph

**Cause (measured, not the one the ticket guessed).** The toolbar used `document.execCommand("formatBlock")`. In Chrome,
`formatBlock p` on a heading does not replace it: it nests a paragraph inside (`<h2><p>text</p></h2>`), and every press added a
level. The caret was then in a `<p>` under an `<h2>`, so the toolbar kept showing H2. Firefox replaces correctly, and `"<p>"`
vs `"p"` makes no difference in either browser. The `focus()` before the command does not lose the selection in either
browser. Neither browser toggled a format off when its button was pressed a second time.

**Fix (`tools/admin/ui/editor.tsx`).** Paragraph / H2 / H3 / Quote are changed on the DOM (`changeBlocks`), not with
`formatBlock`: the top-level blocks the selection touches are replaced by new elements that take their content, and the
selection is put back on the same text. Rules:
- The button of the format a block already has turns it back into a paragraph (H2 twice = paragraph, Quote twice = paragraph).
- A quote is `<blockquote><p>…</p></blockquote>`, the shape the stored HTML already has, so a quote behaves the same before and
  after a save; turning a quote into a paragraph / heading unwraps each paragraph of it.
- Lists, tables and photo / video figures are left alone (the list buttons keep handling lists).
- A bare line on the root (Firefox leaves one after a list is removed) is wrapped as a whole.
- The toolbar state is re-read right after the change. In Firefox `queryCommandState("bold")` is true in every heading
  (computed weight), so inside a heading only a real `<strong>` counts as bold now.

Known limit: a block change is not in the browser's undo stack (the Undo button undoes the typing before it, not the block
change), the same as removing a photo. `formatBlock` was undoable in Firefox only.

## Bug 255: Publish site did not follow the build

**Cause.** The publish state was fetched once on load and then only polled while *this* tab had started a build. A build started
in another tab, by the scheduler, or refused with `409 publish_running` left the button on "Publish site" until a reload, and
the 409 text was only a toast. Nothing checked for unsaved editor changes, and the panel said "about a minute".

**Fix.**
- `tools/admin/ui/app.tsx` `PublishButton`: polls `GET /api/admin/publish` every 5 s while the dashboard is open (2 s during a
  build, paused while the tab is hidden, refreshed when it is shown again). Running → "Publishing…", disabled, ⏳. A 409 shows
  "A build is already in progress. Your changes will be included in the next publish." as a toast and in the panel (kept until
  that build ends) and refreshes the state at once. "Website updated" / "Publish failed" toasts also fire for builds started
  elsewhere. Panel: "Started HH:MM. A build takes about N minutes; the website changes only at the end."
- Unsaved changes: new `tools/admin/ui/unsaved.ts` (a tiny shared flag set by the post editor, the author editor and Settings
  while their state differs from what is saved; cleared on save and on leaving the page). Publish site then shows "Save your
  changes first" and the panel explains "publishing uses the saved posts only"; no request is sent. The same toast can show
  twice in a row (the Toast is keyed by a counter now).
- Build time: `PUBLISH_MINUTES` (default 25) in the service env, returned by `GET /publish` as `minutes` and shown in the panel.
  `.env.example` and `tools/admin/README.md` document it. `errorText("publish_running")` in `api.ts` carries the new wording.

## Tests
- `npm run test:admin`: new case: a second `POST /publish` while one runs → 409 `publish_running`, the running build finishes;
  `minutes` = 25. `npm test`: all suites pass.
- Browser runs (Playwright against the bundled dashboard on a temporary content copy, Chrome 1.63-driven `/usr/bin/google-chrome`
  and Playwright Firefox 1543): paragraph → H2 / H3 / Quote → paragraph, each button twice, H2→H3→Quote→H2 directly, a stored
  quote after save + reload → H2 / paragraph, a selection across two blocks, toolbar states; Publish: press → "Publishing…" at
  once, a second tab shows it within a poll, a tab that believed nothing was running gets the 409 text and "Publishing…",
  unsaved post / author / settings changes block the press and a save releases them, leaving an editor drops its hold,
  "Website updated" on both ends. The harness lives in the session scratchpad (not in the repo).
